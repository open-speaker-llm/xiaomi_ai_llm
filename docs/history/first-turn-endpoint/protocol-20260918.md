# S12A 原生 ASR 结束协议验证（2026-09-18）

> 本文前半部分保留第一轮结论；文末“第二轮”更新了长停顿验证结果。最新状态：12 秒固定录音完整识别通过两次，中间切回原本地等待时长再次失败；自动语音判停及真实首轮尚未接入。

## 结论

在不新增识别服务的前提下，已验证音箱通过原生结束路径通知小米云端，获得包含后半句的完整识别文本。这个结果只证明协议链路可用，尚未证明长句和自然停顿问题已解决，也未部署生产修复。

长停顿对照暴露两层独立限制：云端“没有新识别结果”截断；关闭其协议超时参数后，本地音频引擎仍因等待 ASR 结束超时而停传。不能再把此前约九秒截断笼统解释成网络问题或固定云端总时长上限。

本轮没有 Mac 转写、没有新 ASR 服务，也没有调用 LLM。Mac 仅编译、传输旧测试 PCM 和收集日志。实验通过既有 ASR-only 续听路径软件唤醒并回放，尚非真实首轮用户发声验证。

## 方法和有效样本

固定旧录音裁剪为 7 秒 PCM，内容为“问问 DeepSeek 为什么月亮有时候白天也能看见请用一句话回答”；长样本在“月亮”后的停顿处额外插入 5 秒静音，总长 12 秒。此静音长度是压力测试条件，不是产品拟采用的判停阈值。

有效版本在原生 ASR 上传回调替换测试 PCM，保留原生前端唤醒处理。早期在 DNN 回调替换音频的试验触发 suspect wake，不能用于长句能力结论。试验只绑定确定的 sequence、owner 和 dialog；每次最多 25 秒，输入最多 20 秒；真实唤醒取消回放，同一 sequence 不重新装载。

| 样本 / 模式 | 设备试验目录尾名 | 结果 |
| --- | --- | --- |
| 7 秒 / 0 | `trial.short.0.RaR1bb` | 完整文本；本地主动结束 → RecognizeStreamFinished → final → Finish |
| 12 秒 / 0 | `trial.long.0.5l5nF5` | 约 5.45 秒后提前 final，仅到“为什么月亮”；云端明确报告无新结果截断 |
| 12 秒 / 2 | `trial.long.2.ZiVng9` | 请求确实携带关闭超时参数；本地约 8.4 秒停传，约 11.5 秒收到不完整 final，仅到“有时候” |
| 7 秒 / 2 | `trial.short.2.LlAQQi` | 完整文本，原生 EOF 和 final/Finish 正常 |

模式 0：`asr.vad=false`、`is_using_local_vad=true`、`enable_natural_record_v2=false`；模式 2 额外设置 `asr.tuning_params.enable_timeout=false`。两者都禁用 NLP/TTS，只识别测试音频。

所有完整日志留在诊断主机 `/tmp/xiaomi-endpoint-research/` 下同名目录；不将原始音频、全量设备日志提交仓库。日志快照可能含前次对话，分析必须按下列 dialog ID 过滤。

## 证据

### 原生结束路径

运行时 `create_xaudio` 的第五个参数确认为此固件的 `mipns_oneshot_cb`（0x184c0），code 4 是 vad-end；通过原生事件队列进入 stream_end，再发出 RecognizeStreamFinished。实验校验回调匹配才启用，未从外部盲发不带 dialog 的 STREAM_END。

短样本模式 2，dialog `629524de5a38e5f733df957b99b0880c`，单调时钟毫秒：

```text
492660823 replay loaded: 224000 bytes
492667555 replay finished: 112000 samples
492667874 local-end
492667885 RecognizeStreamFinished
492668072 final: 77 UTF-8 bytes
492668074 Finish
```

final 为完整测试句。EOF 至 final 187 毫秒是这一轮观测值，不是延迟保证。模式 0 短样本也有同样完整链路。

### 云端无新结果超时

长样本模式 0，dialog `99ec92f542cde1e80b44a5d5ca3ce9c8`，服务端返回：

```json
{"received_bytes":180224,"received_stream_finished":true,"truncation_reason":"asr response truncated since no new response"}
```

收到 final/Finish 时，实验尚未回放完毕、也未调用本地结束回调。该通知的 `received_stream_finished` 不能代替设备实际发送 EOF 的时间证据；本地事件记录中的 EOF 在 final 之后。

### 本地等待 ASR 结束超时

长样本模式 2，dialog `ed94e6beb1c5ecbe538376097444df5a`，请求日志确认 `enable_timeout=false` 已发出；本轮未见前述云端截断通知，但仍未成功：

```text
09:34:43.23 左右开始回放
09:34:51.662590 xaudio_engine: wait asr end timeout(6000 ms)!
09:34:51.662666 xaudio_engine: enable asr = 0
09:34:51.671960 xaudio_engine: [wakeup thread] asr send end!
09:34:54.723204 Dialog.Finish
```

本轮没有 replay-finished、local-end 或主动 EOF，不能声称已验证 12 秒完整识别。关闭云端超时后等待更久，但其全部效果仍受本地停传干扰，不能外推为“云端不限时”。

此实验在前端处理之后注入 PCM，前端没有听到回放内容。因此，本地等待超时在真实持续发声时如何触发，仍需验证，不能把实验中的 8.4 秒当作所有真实输入的固定上限。

协议字段依据：[小米 SpeechRecognizer 官方协议](https://cnbj1.fds.api.xiaomi.com/instruction/SpeechRecognizer.pdf?Expires=9223372036854775807&GalaxyAccessKeyId=5151729087601&Signature=+x%2FdatBNDVmYGKTQsoQMMgT8M2o%3D)，AsrTuningParams.enable_timeout。文档存在该参数不等于任意设备/账号都能依此无限延长，以上实测范围优先。

## 后续设计门槛

先查清本地等待计时的起点、重置条件及真实发声下的行为，验证是否能在原生会话内持续收音。不得用永久关闭所有超时替代有限时长、取消和真实唤醒交接机制。

通过该门槛后，再评估音箱端轻量语音活动检测和停顿宽限，控制何时发出已验证的结束事件，继续使用小米 ASR 获取最终文本；不依赖特定呼叫短语，不新增转写服务。简单把所有请求延迟固定秒数，无法补回已停止上传的后半句。

用户提出的“小米回答不了再交 LLM”可保留为路由策略，但前提仍是原始识别文本完整；路由本身无法恢复丢失的音频。初次实际接入前必须覆盖真实首轮、长句、不同停顿、远距离/噪声、超时取消及用户重新唤醒。现有 final-only 修正解决中间结果抢先提交，不能替代上述判停与上传生命周期工作。

## 第二轮：本地计时原因和长停顿对照（10:00–10:02 CST）

### 6 秒计时不是“没有人说话”的直接计时

在相同固件反汇编中确认：

- `set_asr_flag(1)`（0x25998）经 `wakeup_set_asr_end_waiting_flag(...,1)` 启动等待并清零计数。
- `notify_asr_length(len)`（0x2a9ac）在 len 非零时调用同一等待设置函数，重置计数；len=0 直接返回。日志显示非空中间识别结果到达后执行此路径。
- `wakeup_set_asr_end_waiting_flag`（0x25954）及 `wakeup_reset_asr_end_wait_timeout_cnt`（0x258e0）分别设置等待标志和将计数清零。
- `xaudio_wakeup_thread` 在 0x28098 读取等待阈值、累加计数；超过阈值后在 0x28110 调用 `set_asr_flag(0)`。原 `xaudio_vad_get_timeout` 返回 0 时走固件默认值，本设备日志为 6000 ms。
- `set_vad_timeout(float)` 确有实现，但会写共享状态，本实验未调用它。通过专属租约内覆盖 getter 返回值验证，租约外仍返回原值。

因此继续收到 PCM 不代表该保护计时会续期。若中间识别结果迟迟不更新，音频仍在到达也可能停传。这一层是在关闭云端判停/超时之后暴露的保护机制，不能把最初所有日常截断都归因于这 6 秒计时器。

### 单变量回切对照

模式 3 与模式 2 发往小米的请求字段完全相同；唯一行为差异是精确测试租约内将本地 getter 返回值改为 20000 ms。没有改固件、写全局超时配置或关闭所有保护。25 秒租约和最多 20 秒测试 PCM 上限保留。

| 顺序 | 模式 / 试验目录 | 结果 |
| --- | --- | --- |
| 1 | 3 / `trial.long.3.uS6bhQ` | 完整 77 字节文本，384000 字节 PCM 回放完毕，主动 EOF 后 171 ms 获得 final |
| 2 | 2 / `trial.long.2.l8mFTA` | 再次只得到“问问DEEPSEEK为什么月亮有时候”，未回放完、无主动 EOF |
| 3 | 3 / `trial.long.3.DzMOUE` | 再次完整文本；主动 EOF 后 229 ms 获得 final |

成功两轮均有完整 final 与 Finish，未见同 dialog 的 TruncationNotification、StopCapture 或 Exception。基线在最后一次重置（494216503 ms）约 6007 ms 后停传；第一轮成功样本在停顿前后两次重置之间相隔 6431 ms，超过默认的 6 秒。这解释了为什么只改云端参数仍会在后半句刚开始时失去上传。

最新库 SHA256：`1a87b99557546bb630112d4154e7be619ae97592016f388ed3c33a6927417880`。独立设备单测补充了模式、旧 sequence、final、过期和真实唤醒交接后恢复原阈值的检查；原有固件 ABI 回归也通过。

两轮成功、一轮回切失败完成后已主动撤销两个临时挂载，重新验证原脚本哈希、原 preload、native_asr healthy、busy/armed/timer 清除和客户端哈希不变。

## 音箱端 VAD 成本验证

另在音箱独立进程运行 `bench_vad.c`，只读取同一批旧录音，不重启服务、不访问麦克风、不发云请求。使用 [libfvad](https://github.com/dpirch/libfvad) 固定提交 `532ab666c20d3cfda38bca63abbb0f152706c369`，其代码来自 WebRTC VAD；它仅输出语音/非语音，不识别文字，也不能判断语义是否完整。

构建：`zig cc -target arm-linux-gnueabihf.2.25 -Os -UNDEBUG -Wall -Wextra -Werror`，包含 libfvad 的 include/src 路径，编译 `bench_vad.c`、`src/fvad.c`、`src/signal_processing/*.c` 和 `src/vad/*.c`。该固定版本在关闭 assert 时有一个未使用变量警告，因此本次保留 assert，未改上游源码。第三方源码留在诊断目录，未纳入项目生产依赖。

输入为 16 kHz 单声道 s16le，每帧 10 ms。每个模式重复处理 100 次，以进程 CPU 时间除以对应音频时长折算实时计算成本：

| 输入 | 100 次音频时长 | CPU 时间（模式 0–3） | 折算单核占用 |
| --- | --- | --- | --- |
| 7 秒短样本 | 700 秒 | 0.955–0.957 秒 | 约 0.137% |
| 12 秒长样本 | 1200 秒 | 1.607–1.610 秒 | 约 0.134% |

整个测试可执行文件 13332 字节（动态链接系统 libc），峰值 RSS 644 KiB，包括测试驱动和一次装载的 PCM。它们不是集成到原生音频回调后的完整性能指标，但表明本机运行此级别的 VAD 算法成本很低。原始输出：诊断目录 `vad-benchmark-20260918.txt`。

模式 0/1 将短样本句中一段约 730 ms 判为非语音；长样本对应段约 5220 ms。模式 2/3 约为 750 ms 和 5240 ms。这只是 VAD 输出范围，未经人工逐帧标注，不能当作准确率评估。

## 当前可行方案与仍需验证的部分

协议和计算成本已支持这一方向：音箱端判断语音活动 → 保留有限的停顿宽限及总时长保护 → 用原生路径上传音频并发送 EOF → 小米返回最终文本 → 根据原有原生/LLM 路由处理。无需 Mac 常驻、新 ASR 服务或针对呼叫短语的白名单；额外成本主要是端点等待、音频上行时长及固件适配维护。

必须分开两个参数：结束收音的停顿阈值影响响应速度；本地上传保护时限避免识别结果迟到时误停传，后者应覆盖前者与合理通信延迟，不代表每次都等到保护时限。

VAD 无法知道五秒沉默后用户是否还会继续。要允许五秒停顿，就必须承担相应等待，或引入明确续说交互；不能声称靠轻量 VAD 同时实现任意停顿不截断和立即回答。本轮五秒样本只用于证明底层可持续识别。1.2–2 秒可作为后续停顿宽限的对照候选，需用真实停顿、轻声/远距离、电视背景及普通短指令的延迟来决定，不直接写死为生产值。

下一阶段宜先在真实首轮做旁路判停观察，记录 VAD 建议结束点与实际发声的关系，再接入主动 EOF；同时验证云端配置作用域、原生指令、物理唤醒抢占及取消。当前探针仍是有固定音频终点的 ASR-only 实验，不是生产修复。
