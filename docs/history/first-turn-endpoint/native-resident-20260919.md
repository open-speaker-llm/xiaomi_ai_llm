# 长时间运行管理、CPU 续期与回滚边界

接续 [四槽循环验证](native-rolling-20260919.md)。本阶段新增有时限的常驻管理入口，解决旧 240 秒实验上限、累计 CPU 用尽、模型异常退出后的重载，以及回滚旧客户端时旧识别结果的隔离。代码仍在实验目录中，没有安装开机服务或改变日常部署。

## 长时间管理

`run_native_wake_session.sh resident [秒数]` 默认 3600 秒，支持 37–86400 秒，内部由 `native_resident_session` 管理 `native_wake_pool` 及其唯一模型子进程。它是音箱上的进程管理层，不涉及 Mac ASR、外部服务器或第二份模型并行推理。

- 原四轮及显式有限轮数入口保留原有上限。常驻入口仍有明确总时限及 10000 轮预算，不是无限期授权。
- 单次唤醒的收音、模型积压、输入停滞和请求超时限制不变。到总期限前 31 秒，在空闲时撤销接管；已开始的请求可以按原有单轮预算完成，随后不再开启新代际。
- helper 死亡时，控制器保留旧 pending，回收音频资源。管理器退避后启动新的控制器和模型，新 owner / observer / nonce 与旧轮隔离；配置或外来状态错误直接退出，三次运行失败后停止，避免不断加载模型。
- 临时忙碌不消耗故障次数。管理器和控制器通过直接父子关系及 Linux 父进程死亡信号连接，不用旧 PID 文件盲杀进程。管理器有独立内核锁和 stop socket，恢复入口先停止管理器，再停止普通 session。
- 管理器只处理模型/控制器生命周期；真正唤醒仍由原生回调同步认领已准备的输入区。

临时前端也有自动恢复期限。`native_resident_lease.sh` 要求原生探针与实验客户端的定时器都至少覆盖请求时长加 30 秒，否则常驻入口拒绝启动。两个 setup 的 `NATIVE_WAKE_RESTORE_SECONDS` / `NATIVE_ROUTE_RESTORE_SECONDS` 可以显式设置 60–86520 秒，默认仍为 300 / 480 秒。不能只把模型入口改成长时间，却让前端五分钟后自动撤销。安装时需包含构建产物中的 manager、restore guard 和对应 shell 库。

## CPU 与空闲成本

旧的 `ulimit -t 90` 是整个进程累计 CPU 时间，正常使用多轮后也会耗尽。现在保留 96 MiB 地址空间限制，将 CPU 设置为可续期软限制：helper 每秒读取自身 CPU 消耗，将软限制推进到累计消耗向上取整加 15 秒；继承的硬限制不提高。推理卡住时无法续期，Linux 内核仍能停止该进程。

`neural_cpu_lease.h` 不按墙钟时间扣除空闲预算。独立 ARM 测试确认正常续期超过初始预算仍可运行，不能提高既有硬限制；刻意不续期的忙循环子进程被 SIGXCPU（24）终止。主机 macOS 未获得同样的软限额信号表现，Linux 信号测试在主机明确跳过，不能将主机设置限额成功视为 ARM 执行保护已验证；ARM 有独立的实际信号证据。

静置测量发现，控制器此前每 10 ms 把未改变的 pool 状态重写一遍。改为仅状态变化时写入；常驻空闲检查降至 50 ms，有音频后仍用原来的处理频率。下面的 CPU 与内存数字由私有审计文件保存，属于短时样本，不能替代全天稳定性测量。

## 本轮实际结果

音箱独立测试以 360 秒期限运行，控制器 2441、模型 2443。READY 后静置 250 秒，再按实时速度回放“正常结束 → 语音中取消 → 正常结束”，两次正常轮候选均为累计音频 3940 ms，重置 12 ms，最大积压 5 帧（原拒绝上限为 25 帧）。原生上传和麦克风没有参与此测试。随后在期限前 31 秒的空闲期撤销接管并正常退出；不能把它写成已经连续运行一小时或一天。

控制器加模型的空闲 CPU 按设备实测 `CLK_TCK=100` 计算：旧实现 60 秒消耗 154 ticks，约为单核 **2.57%**；优化后 250 秒消耗 183 ticks，约 **0.73%**，本次样本下降约 **71.5%**。不含日常原生进程及外层管理器。静置期模型 RSS 28120 KiB，三轮回放后 28420 KiB；映射文件保持 12 个，模型内存映射 59 个、文件描述符 3 个。

随后实际杀掉独立模型 3759：管理器等待两秒，重新加载约 1.94 秒，新的控制器/模型为 3909/3911。旧请求保持 pending，新轮回放获得 3940 ms 候选及有效 quiet。恢复约四秒期间使用原生回退，不能宣称故障恢复没有空窗。再杀掉管理器，验证子控制器和模型撤下、下一次启动成功，stop 清理 resident / session socket。

最终主机回归 **195 项、194 通过、1 项 Linux 信号测试跳过（123.208 秒）**，该信号测试已在 ARM 独立进程实际通过；shell 检查及 ARM 严格编译通过。较早的一轮全量测试中，旧有一秒期限的 worker 清理测试未观察到清理输出；没有修改其实现或预期，最终全量复跑通过，首次失败原因尚未单独证实。CPU 软限额的主机/设备差异单独记录于上一节，未把跳过项计为主机通过。

## 回滚修正

源码复核纠正了上一阶段的一个隐含前提：SHA256 为 `70a7012f…f184` 的日常旧客户端既不读取压缩拒绝表，也不读取逐条 endpoint journal。因此“把压缩 ID 展开为逐条记录”仍不能保护那个旧版本。

新 `native_route_restore.sh` 把回滚建立在完整的原生进程边界上：

1. 校验原客户端，停止管理器/控制器与当前实验客户端。
2. 停止两个原生服务，确认 mipns / aivs 进程均不存在。
3. 在服务保持停止的情况下撤下实验 overlay，再次确认没有旧写入进程。
4. 将旧 `instruction.log` 移入新的私有 rollback 目录，保留证据；不删除拒绝表或历史对话。
5. 启动日常原生服务，再启动旧客户端。旧客户端只会看到新原生会话产生的结果。

任何失败都保留 armed 标记，不报告恢复完成；下一次尝试新建证据目录，不覆盖上次归档。旧客户端已启动但上次确认失败的情形，重试可停止已核实路径的那个客户端再建立新边界。错误或不明 PID 记录拒绝处理。

`native_restore_guard` 让原生定时恢复与完整客户端恢复共用内核锁；锁保留在短时管理父进程，不会被重新启动的日常客户端继承。并发恢复被拒绝，内部恢复步骤保留同一保护上下文。stop、overlay 或归档失败、旧写入进程残留、源日志为符号链接均不能提前启动旧客户端。

回滚流程通过主机故障注入与音箱 BusyBox 的隔离目录测试。测试中的服务启动/停止是替身，没有在本轮重启日常原生服务；完整设备回滚流程仍需配合接入测试验证，不能把上述单元验证写成生产回滚已经演练。
