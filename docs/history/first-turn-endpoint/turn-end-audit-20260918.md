这里用 ASR 结果到达时间推演，不能读取未来 final 来决定之前应该何时结束。seq 32 在 7233 ms 收到“为什么月亮”，11080 ms 才有下一次进展，间隔 3847 ms。两秒稳定策略会在 9233 ms 触发。没有 PCM，不能把这个间隔直接称为用户停顿，可能包含识别延迟或其他此前未解因素；但这已说明“文字不变＝问题结束”缺乏可靠依据。

同理，不把“两秒稳定且文字像完整问句”当成已解决：这需要额外语义判断，且一句完整问题之后仍可能补充条件。普通关键词/句式匹配不是普适办法；逐轮请求额外 LLM 判断也增加网络依赖、成本和延迟。

## A 的具体 VAD 现象

小米最后可用 ASR end offset 为 7240 ms。之后模式 1 有阳性片段：7240–7530、7780–7870、8420–8520、8710–8930、9770–10570、11490–11600 ms。按当前连续 120 ms 确认规则，220 ms 和 800 ms 段会重置句末计时，最后确认位置移到 10570 ms，故到 12570 ms 才结束。

模式 2/3 也保留了后段活动，候选只比模式 1 早约 0.1 秒。简单换灵敏度并没有在本样本解决拖延。抬高连续语音时长门槛去滤除 800 ms，又可能丢掉真正继续说的短词。日志仅在 VAD 边沿记录能量，不能将这些点当成整段均值、噪声底或用来校准幅度门限。

以上说明程序为何延后，但不能确认声音来源：没有保留 A/B PCM，不能将用户“无干扰”反馈改写为有背景人声，也不能认定一定是 VAD 自身错误。

## 可行的下一步

先取一轮与 VAD 完全同源的短音频，再区分：

- 后段实际是非语音声：评估音箱端轻量降噪或噪声自适应的必要性，以轻声/续说反例验证，不凭 A 单例设幅度阈值。
- 后段仍有真实语音：单一 VAD 不能识别是否属于提问人，需明确可接受的环境/交互边界，不能称为算法误判。
- 输入与听感不符或有旧内容：查原生输入缓冲和通道，再改判停规则。

已有小米非空 partial 可以作为“已开始提问”的辅助信号；不能直接作为“已结束”的充分条件，也不能靠它解决所有背景人声。真正提交 LLM 仍只能使用当前会话完整 final。上述方案无需增加独立识别服务；音箱端处理开销需要在确定方案后实测。

`capture.armed` 私有文件绑定当前 sequence/owner；只有模式 5 的已绑定有效租约才复制原生 ASR callback 输入。默认关闭，真实唤醒会撤销并清空，同一已取消轮次不能重启采集。内存上限 640000 字节（16 kHz 单声道 S16LE，20 秒），每轮清空，实时回调只 memcpy，不做文件写入。到受控本地 EOF 后才保存私有、不可覆盖的独立 PCM 文件，再由 runner 收入试验目录 `input.pcm`。取消、超时等没有受控 EOF 时可能没有录音，不能把缺少文件当作静音。
