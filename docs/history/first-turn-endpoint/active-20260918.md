## 判停与归属

- libfvad 固定 `532ab666c20d3cfda38bca63abbb0f152706c369`，mode 1，16 kHz，10 ms 帧。
- 连续 120 ms VAD 阳性确认语音，随后连续 2000 ms 没有新的确认语音才结束。
- 静音截止点上刚开始的语音，会暂缓决定直到确认或消失；90 ms 短脉冲不能把静音起点不断后移。所有音频仍上传，不丢弃未确认片段。
- 未确认语音最多等 8 秒；全轮最多 20 秒。音频时间和单调墙钟都设上限，回调停滞不能无限等待。
- 原生本地保护计时器仅在精确试验租约内读取为 25 秒。它是兜底，并非正常响应等待时间；不调用全局 setter。
- 每轮必须匹配 sequence、owner、deadline、BOUND dialog、当前 mipns PID、存活的 aivs；结束前再检查 armed 文件和模式。final、取消、owner 消失、新唤醒、进程替换、静音或到期不能让旧轮结束回调落入新轮。
- 新物理唤醒撤销本实验，恢复原生会话；同一 sequence 不可重新装载。开始、PCM 回调和本地结束沿既有 wake_dispatch_lock 串行。
- 临时 init 脚本通过 bind mount 覆盖，校验四个固件哈希，五分钟独立恢复计时器。恢复只卸载仍与本实验哈希一致的覆盖层。

这些延迟是四次样本观测，不是网络性能保证，也不含 2 秒停顿判断和后续 LLM/TTS。

## 尚待验证与首轮接入条件

实时麦克风第一轮 `trial.microphone.5.B5XGsf`（seq 29）返回完整“为什么月亮有时候在白天也能看见请用一句话回答”，但原因是 **hard-limit**：音频 20000 ms、墙钟 19752 ms，最后确认语音仍在 19200 ms。EOF 到 final 95 ms。这不是正常句末判停通过，不能仅凭完整 final 宣称方案成功。该轮没有保存 PCM，无法事后判断 VAD 阳性片段的具体声源。原配置已恢复，日志在 `active-trials/` 和 `live-active-restore.txt`。

因此先暂停首轮接管，补充模式 1/2/3 并行观测与 VAD 转换处的信号能量记录；更严格模式只做旁路比较，不影响结束决定。诊断不保存新音频，不通过文字关键词补丁规避误判。初版二进制哈希对应上面的五轮结果，添加诊断后的二进制为 `e27f86bad97b8ef3d4e0924a25f3eeed2ae04655992e31512818695188bcc7bf`。

2 秒不是语义完成检测，超过该时长的思考停顿仍可能被截断；连续电视人声可能延迟结束。小于确认窗口的极短轻声命令可能等到 8 秒上限，需增加短命令样本后再选择参数。

首轮不能直接复用 ASR-only 会话去替代原生 NLP。应保留小米原生指令执行与回答，只改变当前首轮的上传结束条件；识别完成后再沿既有路由决定是否转交 LLM。实现需独立验证：物理唤醒世代与 prepare/Recognize 的归属、连续两次唤醒时拒绝不明确的绑定、旧 StopCapture/Finish 对新轮的隔离、唤醒提示音与播放泄漏、取消后不再发 EOF。相同的 prepare 负载可能重复，仅凭内容哈希不能证明新旧物理会话归属。

本次判停模块可作为继续验证的实现基础；首轮接入不能省略上述归属与真实环境验证。

## 并行灵敏度观测的反例

随后 `trial.microphone.5.jwrdOg`（seq 30）原计划作为安静对照。用户随后说明，刚才已经离开电脑旁，并且可能存在其他声音干扰；离开时刻与具体试验轮次无法精确对齐。故撤销“安静对照”标签，改为环境未受控样本，不能据此认定检测器在安静环境下误判，也不据此否定音箱端 VAD 方案。该轮三种模式都达到 20 秒上限，没有正常句末候选：

| libfvad 模式 | 20 秒内原始 VAD 阳性时长 | 最长连续 VAD 阴性 |
| --- | --- | --- |
| 1 | 17750 ms | 260 ms |
| 2 | 15000 ms | 290 ms |
| 3 | 14990 ms | 290 ms |

小米同时生成多次渐进 partial，内容是与月亮问题无关的连续对话，和用户补充的可能干扰相容，但具体声源仍未确定。若是背景人声，普通 VAD 将其判为语音可能是正确检测；区分它是否属于正在提问的人，是另一项能力。故不直接把主模式换成更严格模式；旁路 2/3 仅证明单改模式没有解决这轮环境下的持续收音。

该轮另有原生 SDK 失效：最后一次 ASR 文本进展附近为 20:12:09.064；20:12:19.071 记录 `50010005 TTS timeout` 并重连；本地硬上限到 20:12:19.172 才发送 vad-end，此时 worker 已 idle，未形成对应的 RecognizeStreamFinished。CLI 到租约截止返回 124，state 为 FAILED、final=0、finished=0。**不能把这次 124 当成正常无语音完成**，与前面的人工零样本不同。

下一步需确认实时输入声源/原生处理通道，并研究 SDK 在 ASR-only 请求期间仍等待 TTS 的条件与失效通知。当前 20 秒上限只能限制本地等待，不保证赶在 SDK 内部超时前正常结束。此次没有临时抬高 SDK 全局超时，也没有将 partial 交给 LLM。实验已经主动恢复。

用户补充环境情况后，仅离线复核既有日志，没有重新启动收音。已确认顺序为：最后一次 partial 处理完成 → 约 10.008 秒后 SDK 报 TTS timeout、主动清理并重连 → 原生采集状态转 idle → 约 100 ms 后实验才发 vad-end。超时前仍有音频写入日志，因此不能将该次失败直接归因为断网；但仅凭此轮也不能证明所有 SDK 超时路径都采用相同计时值，仍需确认其内部条件。精确筛选时间线保存在忽略目录 `timeout-sequence.json`。

### 发现：开始条件与结束条件需要拆开

模式 2/3 的候选都早于该轮小米首次识别语音的 begin offset；结合逐步识别日志，它们发生在本轮目标问题开始之前。因此不能把 6520 / 2980 ms 当作“更快的正确句末”，直接换成更严格模式会导致还没问就结束。

模式 1 在用户开口之前及问题结束之后也出现多个超过 120 ms 的 VAD 阳性段。当前“任意连续 120 ms 阳性即确认开始”的方法不够稳健，短声音既能错误启动句末计时，也能反复延迟结束。后续需要分别验证提问开始资格与句末判定，例如利用既有小米识别进展辅助确认已经开始提问；这只是候选设计，不能把 partial 当最终问题，也不能假定它没有网络延迟或背景人声误识别。
