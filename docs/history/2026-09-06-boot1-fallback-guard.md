# 2026-09-06 boot1 失败提示拦截修复

当前结论：2026-09-06 已在 S12A 的 boot1/system1（ROM 1.76.54）实测：匹配到的小爱失败提示可被拦截并转 LLM，修正版重启后用户确认正常转接、没有先播失败提示。判定仍依赖文本规则，未知文案可能漏判，正常回答含相似词也可能误判；不保证所有文案、时序或固件都无漏音。

## 复现证据

用户报告原生答不了的问题在转 LLM 前可能先播“我还不会、要学习”。当前 system1 原生链路在 think 阶段不能沿用 boot0 的提前冻结，原有 shell 在失败文本出现后才暂停 mediaplayer，存在漏播窗口。

本轮原样测试“人类可能实现 AGI”时，还复现了完全不转 LLM：云端实际回复“这可把我难住了，看来要更努力学习了”，原有失败正则没有匹配，客户端等候结束回到 IDLE。该轮 ASR 将 AGI 识别成 AGM，未修改或伪造识别结果；路由遗漏的依据是明确的失败播报文本。

## 改动

- 默认失败表达式覆盖“难住 / 问住”和第一人称再次、多、继续、努力学习的表达，shell 与 helper 共用同一表达式。
- 增加 `aivs_speech_guard`：仅在 boot1 当前会话激活时读取新增完整 AIVS JSON，匹配失败 Speak 后立即暂停 mediaplayer，由原状态机接手转 LLM。
- 未命中规则的原生播报放行，ASR 进程不暂停；helper 不改麦克风、系统分区或音量配置。正常原生回答含匹配词时仍可能误判。
- helper 只释放自己尚未被接手的暂停，三秒内无人接手或客户端退出时恢复；缺少 helper 时保留原有轮询。
- `/data/native_first_client.sh` 与 `/data/aivs_speech_guard` 持久安装，沿用已有 `/data/init.sh` 自启动。用户配置未改写。

## 验证范围

- 原问题：用户先确认旧版本未转 LLM。
- 临时修复后，两轮用户均确认正常转 LLM、未听到先行失败提示；时间查询完整正常。
- 设备日志观察到对应 `GUARD_BLOCK` 与后续 LLM 路由，结束后播放器恢复。时间播报未产生对应失败拦截。
- 完整自动测试 24 项通过，含实际 C JSON/Unicode 解析、遗漏文案、成功播报与非 Speak 指令放行、错误 JSON、暂停所有权、boot0 不启动 helper、缺少 helper 保留原轮询；shell 语法检查通过。
- C 同时经本机编译器和 aarch64-linux-musl 静态交叉编译通过（启用警告并视为错误）。
- 正式安装后重启到 boot1，确认 `/data/native_first_client.sh` 和 `/data/aivs_speech_guard` 自动启动、hook 安装成功并进入 IDLE；两份文件哈希与通过听觉测试的版本一致。

同一句意图的云端回复可能变化；已遗漏的“更努力学习了”文案另由回归测试验证。上述听觉结论来自这次用户实测，不保证任意未知文案或固件都完全无漏音。

## 后续复测：同义失败文案仍漏匹配

首版持久部署后，用户再次发现未转 LLM。核对运行文件哈希、客户端和 helper 进程后，确认部署仍有效；本轮云端回复换成“被难住了诶，看来我还要再学习一下”，不匹配首版仅列举的“把我难住了”等表达。

新增回归测试先复现 shell 与 helper 的两项失败，再将有限原句改为失败表达族。新增样例同时验证 UTF-8 与 Unicode 转义；音箱实际 aarch64 helper 的 16 个分类样例也通过，测试没有发送暂停信号。

再次替换正式客户端并重启。首版两次听觉通过不能代表所有文案已覆盖。修正版重启后，用户确认正常转 LLM、没有失败提示；本轮原生返回“这个问题把我难住了，我会继续努力的”，日志对应 `GUARD_BLOCK`、unsupported、LLM 调用及最终 IDLE。此前漏掉的“被难住了诶，看来我还要再学习一下”由 shell/helper 回归测试和设备端分类测试验证。

## 历史判定方式与状态字段复核

- `2e06ab9`（2026-06-03）最早提交尚无 boot1 专用适配：通用路径读取 `nlp_result_get`，已有失败文本辅助、`michat/model` 和原生能力白名单路由。
- `2371819`（2026-06-07）加入 boot1 AIVS 适配，从一开始就是提问触发词/失败 Speak 文本匹配，匹配后客户端自己填入 `michat/model`。现有 Git 历史未发现已正常工作的 boot1 独立失败状态判定阶段。
- 历史 `nlp_result_get` 与 mibrain 记录文件、ubus monitor 的比较见 [旧调试记录](../archive/2026-06-07-pre-doc-reorg/DEV_COMMANDS.md)。boot1 的旧接口可能不刷新，不能拿旧缓存判断当前提问。
- [追问实验](followup-exploration.md#83-实测注入-0x03--0x01-仍被拒) 出现过 `finish open_mic:0, valid_speech:0, valid_speak:0`，但没有证明这些值能区分业务回答成功/失败，也没有证明 finish 时仍来得及拦播。本次未实现免唤醒追问。
- 本次收益来自 shell 约 0.2 秒轮询之外的 C 快速监听（约 10ms 检查间隔）与规则补全；这不是硬实时延迟保证，也不是新发现了业务状态字段。
- LLM 回答不参与原生失败文本分类；LLM 请求和播报期间的 busy 标记还会禁用 guard 拦截。小爱原生正常回答包含匹配词时仍可能被误判。
