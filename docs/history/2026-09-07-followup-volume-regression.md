## 比较证据

旧快照 `/private/tmp/xiaomi-first-wake-20260907/native_first_client.log`：21:16:34 首轮 Master=155；21:16:47 第二轮记录 reuse session LLM Master=145，加原有 10 补偿后仍为 155。该轮 21:16:50 至 21:17:24 正在播报 AGI；同目录 messages 在 21:16:56、21:17:07、21:17:17 记录真实唤醒，其中 21:17:19 最终识别“开灯”。

当前日志：首轮 Master=155；追问开始时重新读取原生 media volume=150，加补偿后变为 160。例如 22:34:13 第二轮如此。前一轮记录中也多次出现。配置中的音量比例、限值、补偿没有改动。

原因：追问真实唤醒交接修复将 finish_llm_playback 提前到开启续听之前；该清理函数会通过 restore_llm_master_volume 清空 LLM_SESSION_MASTER_TARGET。因此每次追问都丢失当前会话缓存，下一轮用不同原生 media volume 重算，导致音量变化。

音量上升是确定的代码回归；它可能增加回声和唤醒困难，但尚不能证明是灵敏度变化的全部原因。之前和当前日志 is_aec_scene 都有 0，不能用这个值单独推断算法被关闭。

## 修复与测试

wait_native_live_asr 保存 LLM 的会话音量目标，完整执行原生队列清理和音量恢复后再恢复缓存。普通追问沿用同一会话目标。实际交给原生时只清空逻辑缓存，不改新原生对话音量。超时/正常结束由既有最终清理清除缓存，防止污染下一会话。

新增行为测试在实际 shell 函数上先失败，旧代码明确输出 next-answer:160；修正后输出 next-answer:155。覆盖有文本、静默超时、物理唤醒交接三个结果，均验证开麦前原生 Master=145、恢复状态清空；结束时缓存清空。90 项测试与 shell 语法检查通过。
