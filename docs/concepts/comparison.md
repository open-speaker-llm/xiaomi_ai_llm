# 接入路线与本项目的取舍

小爱音箱接入大模型，可以从不同层介入。理解介入位置，比先比较模型数量更有帮助：它决定谁负责唤醒、谁拿到识别文本、谁控制播放，以及升级时要维护什么。

## 三种介入位置

| 路线 | 基本思路 | 主要取舍 |
|---|---|---|
| 云账号接入 | 通过账号相关接口读取对话或控制播放 | 减少硬件改造，但依赖账号接口与外部程序 |
| 接管音频 | 客户端与服务端自行组织采集、识别和播放 | 可自行设计交互，同时承担音频和原生功能兼容工作 |
| 本机原生优先 | 在设备上复用原生识别结果，按规则接入 LLM | 保留原生链路，但需要设备权限与固件适配 |

这是架构层面的分类，不是对具体项目当前支持机型、功能数量或维护状态的实时评测。原有横向资料采集于 2026-06；了解最新能力应直接查看 [mi-gpt](https://github.com/idootop/mi-gpt)、[xiaogpt](https://github.com/yihong0618/xiaogpt) 与 [open-xiaoai](https://github.com/idootop/open-xiaoai) 的仓库说明。

## 本项目为什么走原生优先

这台老音箱已经拥有可用的唤醒、原生语音前端和家电控制。复用这些部分，可以把工程重点放在它不擅长的开放问答，以及 LLM 播放后如何继续聊。

音箱能够自己运行 LLM/TTS 客户端，不需要额外的小米云账号轮询程序；选择端侧 TTS 和原生追问后也不需要常驻电脑。代价是需要串口、SSH、匹配的固件和持续的组件维护；当前只实测一个型号，云识别与模型服务仍然是依赖。

## 这些取舍怎样影响使用

- **原生能力继续存在**：客户端按系统读取结果，选择原生或 LLM。boot1 仍依赖失败文案规则，不能保证所有提问都路由正确。
- **对话可以自然延续**：boot1 使用原生 ASR-only 做上下文追问，首轮可选本机 VAD 容纳停顿；这两条入口都有适配与验收条件。
- **维护要跟随接口变化**：固件 ABI、原生服务行为和 EdgeTTS 协议变化都可能需要重新适配。校验失败时按组件说明恢复，不能仅修改哈希白名单。

当前能力和待验证项见[状态页](../status.md)。理解实现可以继续读[一次对话的完整过程](native-first.md)；想看路线如何从多次实验中形成，读[探索故事](../history/journey.md)。
