# 与同类开源项目对比

把本项目放到小爱音箱接入 LLM 这条赛道里横向看一遍：它和 [open-xiaoai](https://github.com/idootop/open-xiaoai)、[mi-gpt](https://github.com/idootop/mi-gpt)、[xiaogpt](https://github.com/yihong0618/xiaogpt) 各走了什么路线、强弱在哪、有哪些可以互相借鉴。

> 表中其它项目的信息基于其公开 README（采集于 2026-06），可能随上游更新而变化，以各自仓库为准。

## 一张表看清差异

|---|---|---|---|---|

## 三种接入哲学

这些项目本质上是**三种完全不同的接入哲学**：

1. **云账号路线**（mi-gpt / xiaogpt）：不碰硬件，用小米账号当"遥控器"——轮询云端拿到"小爱听到了啥"，再通过云端让音箱说话。**最易用**（pip 装一下 / Docker 起一下），但①依赖小米云接口，小米一改 API 或封号就废；②有云端轮询延迟；③对话过小米云。

2. **刷机接管路线**（open-xiaoai）：把音箱的耳朵嘴巴整个夺过来。**功能最强**（真打断、自定义唤醒词），但①要全量刷机有变砖风险；②只支持 2 款新机；③已停更。

3. **本机原生优先路线**（本项目）：不夺权、不轮询云，而是在**音箱本机**读小米自己的 NLP 结果，只接管它答不了的问题，LLM/TTS 客户端也运行在音箱上，联网调用对应云服务，不是在音箱本地运行大模型或语音合成模型。

## 本项目的实现重点

- **按系统保留原生能力**：boot0 使用 `domain/action` 与失败文本辅助；boot1 使用 AIVS 提问/失败文案规则。2026-09-06 已在 S12A 的 boot1/system1（ROM 1.76.54）实测：匹配到的小爱失败提示可被拦截并转 LLM，修正版重启后用户确认正常转接、没有先播失败提示。原生报时也实测完整正常。判定仍依赖文本规则，未知文案可能漏判，正常回答含相似词也可能误判；不保证所有文案、时序或固件都无漏音。详见 [实测记录](../history/2026-09-06-boot1-fallback-guard.md)。

- **音箱端直连 TTS**：`device/ettsc/` 使用阻塞网络 IO 与 OpenSSL，在音箱上连接微软 EdgeTTS 云服务。无需常驻 Mac，仍依赖联网；构建与部署见 [组件说明](../../device/ettsc/README.md)。

- **boot1 原生实时追问**：2026-09-06 已通过 NONWAKEUP 上行入口创建新的 ASR-only 会话，用户实测西湖问题的上下文追问成功，Mac 识别服务停止期间仍可工作。旧 ExpectSpeech 下行注入失败不能否定此路径，见 [实测记录](../history/2026-09-06-boot1-native-followup.md)。

## 定位与取舍

- **可脱离常驻电脑**：原生识别和音箱端 LLM/TTS 客户端配合运行，不需要额外的小米云账号轮询程序；仍依赖小米原生云服务、LLM API 和所选 TTS 服务。
- **安装和适配成本较高**：需拆机接串口，目前仅实测 MDZ-25-DA / S12A。原生追问组件限定已校验的 boot1 固件。
- **维护边界明确**：云接口、EdgeTTS 版本和固件 ABI 变化都可能影响功能；固件校验不通过时拒绝加载原生追问组件，按已保存的备份回退。

## 可借鉴 / 未来方向

1. **从功能接通转向持续验证**。boot0/boot1 的核心能力已基本齐备；下一步应比较相同问题的路由差异、噪声环境识别、收听结束时机与长时间运行。当前两套系统都没有播放中语音打断；boot1 新的提示音静音补丁仍待听觉复验。对照见 [双系统能力表](native-first.md#双系统能力对照2026-09-06)。

2. **轻量入门档**。云账号路线 `pip install` 就能用，本项目要拆机。可借云账号路线做一个低门槛入口：让没勇气拆机的人先用 miservice 方式尝鲜，确认喜欢再上"本机自治"完全体。

3. **EdgeTTS 版本过期自愈**。本机 EdgeTTS 依赖 `Sec-MS-GEC-Version`，微软抬高门槛时会 403 静默降级到原生音色。可做"403 精准报警 + 版本自动更新 + 缓存重试"，让这条少依赖路线更耐老化。
